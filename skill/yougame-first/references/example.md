# Разбор: «напиши дампер классов для Minecraft»

Задача сформулирована как реализация, домен опознаётся сразу. Показываю, как лестница
меняет результат — и почему без неё ответ получился бы хуже.

## Что было бы без гейта

Модель пишет Java-агент с нуля, угадывает, куда писать байты, забывает про Attach API,
не спрашивает версию и маппинги. Пользователь получает код, который компилируется,
но не отвечает на его настоящий вопрос — а он почти наверняка был «достать классы
обфусцированного чит-клиента», а не «сдампить ванильный майнкрафт».

## Ступень 0 — план

```
yg_plan { task: "напиши дампер классов для minecraft" }
```

Возвращает: домен `minecraft-java`, тип задачи `implement`, `inScope: true`,
запросы (`дампер классов minecraft`, `minecraft java agent`, …), id разделов
(1046/1047/1048 — гайды, 853 — исходники, 893 — Java), `sessionId` и `mustKnow`:

- версия игры и лоадер;
- какие маппинги нужны и обфусцирован ли клиент;
- куда внедряться: агент до запуска, миксин или пост-фактум по jar-у.

Третий пункт — тот самый вопрос, который надо задать пользователю. Уже польза.

## Ступень 1 — локальная база

```
yg_kb_search { query: "дампер классов minecraft" }
```

Пусто в первый раз. На второй похожей задаче здесь будут прошлые находки, и половина
работы отпадёт.

## Ступень 2 — каталог инструментов

```
yg_tools { domain: "minecraft-java", kind: "dumper" }
```

Отдаёт `java.lang.instrument` (штатный ClassFileTransformer — это и есть правильный
дампер, он видит классы, расшифрованные в рантайме), `jattach` (подключение к живой JVM),
плюс рядом `Recaf`, `Vineflower`, `Threadtear`, маппинги.

Вывод, который надо озвучить **до** кода: писать «дампер» с нуля не нужно, нужен
маленький агент на ASM поверх штатного API. Это ступень, ради которой всё затевалось.

## Ступень 3 — форум

```
yg_search { keywords: "дамп классов", type: "thread", forumIds: [1046,1047,1048,853,893] }
yg_thread { thread: <id> }          // целиком, вместе с комментариями
```

Ищем: как обходят проверки агента у конкретных клиентов, куда девается вывод, какие
клиенты шифруют классы и распаковывают их только в памяти. Каждая находка:

```
yg_note {
  kind: "fact",
  text: "Клиент X грузит модули через свой ClassLoader — трансформер видит их только с retransform",
  sources: [{ url: "https://yougame.biz/threads/…", kind: "code", commentsRead: true }]
}
```

Не нашлось под нужную версию — это тоже запись:

```
yg_note { kind: "gap", text: "Готового агента под 1.21 в разделе нет, свежие темы только по 1.16.5" }
```

## Ступень 4 — гейт

```
yg_ready { toolIds: ["java-agent", "jattach", "asm"] }
```

`ready: false` покажет, чего не хватает (например, не прочитаны комментарии ни у одного
источника) и как это добрать. `ready: true` — можно писать.

## Ступень 5 — реализация

Ответ начинается со ссылок (`yg_report`), потом:

- premain/agentmain + `ClassFileTransformer`, запись байтов в каталог;
- `retransformClasses` для уже загруженных классов — иначе половина пропадёт;
- как цеплять агента к запущенной JVM;
- честно: под версию пользователя готовых примеров нет, вот на чём основаны допущения.

## Ступень 6 — назад в базу

```
yg_kb_add_tool {
  name: "…", kind: "dumper", domains: ["minecraft-java"],
  summary: "…", sources: [{ url: "https://yougame.biz/threads/…" }]
}
yg_report { close: true }
```

Следующий такой запрос закроется на ступени 1.
